# Module: torrent

**Gradle path:** `:torrent`.

## Responsibility
- `TorrentEngine` interface (see ADR-0001): add magnet / .torrent, metadata, file list, per-file priorities, pause/resume/remove, stats `Flow` (progress, speed, peers, ETA, ratio), resume data.
- jlibtorrent 2.x implementation (`JLibTorrentEngine`), running in a foreground service independent from the player.
- Automatic priority 0 for samples/images/extras; download only the movie file and `.srt`/`.ass`.
- Persisted resume data so downloads continue after reboot.
- Designed from day 1 for stream-while-downloading: piece-deadline / sequential window API around a playback position (`prioritizeWindow(fileIndex, byteOffset, windowBytes)`), even if phase 8 implements it later.
- Window and readiness API on `TorrentEngine` (#93; ADR-0001 §4, decided on #32):
  - `prioritizeWindow(id, fileIndex, byteOffset, windowBytes)` promises that the pieces covering `[byteOffset, byteOffset + windowBytes)` of that file are fetched ahead of the torrent's normal order, so playback can read ahead of the download.
  - `prioritizeRanges(id, fileIndex, ranges: List<FileByteRange>)` (#245, additive) is its multi-range form: it replaces the torrent's one window with the pieces of every range at once, deadlines in the order of `ranges` -- what the playback gate needs, since head, tail and a mid-file start buffer are not contiguous. `prioritizeRanges(id, i, listOf(r))` equals `prioritizeWindow(id, i, r.offsetBytes, r.lengthBytes)`; either call replaces the other's window, `clearWindow` clears both.
  - `clearWindow(id)` drops that window and returns the torrent to its normal piece order.
  - `rangeReadiness(id, fileIndex, byteOffset, lengthBytes): EngineResult<RangeReadiness>` is the query playback uses before opening or resuming an incomplete file (epic #8): `RangeReadiness(ready, readyBytes, missingPieces)` says whether every covering piece is on disk, how many bytes are contiguous from `byteOffset` (at most `lengthBytes`), and which covering pieces are missing (ascending). `UnknownTorrent` for an unknown id, `NotReady` before metadata.
  - `PieceWindowCalculator.piecesFor(fileOffsetInTorrent, pieceLengthBytes, totalPieces, byteOffset, lengthBytes): PieceRange` is the pure arithmetic behind both: a file-relative byte window to absolute piece indices, clamped to `0..totalPieces - 1`; `lengthBytes <= 0` means the single piece containing `byteOffset`.
  - `FakeTorrentEngine` implements all three: `setPieces(id, pieceLengthBytes, have)` sets its piece model (files laid out back to back in `emitMetadata` order; default 256 KiB pieces, none on disk), `rangeReadiness` answers from it through `PieceWindowCalculator`, and `lastWindow(id)` returns the last `prioritizeWindow` (fileIndex, byteOffset, windowBytes) until `clearWindow` (null after a `prioritizeRanges`); `lastRanges(id)` returns the current window as (fileIndex, ranges) from either call. `JLibTorrentEngine` implements all three since #94 (below).
- `com.teachermovies.torrent.policy`: pure Kotlin status-mapping policy, kept separate from any adapter so it stays engine-agnostic. `RawStatus`/`RawPhase` mirror libtorrent's `torrent_status::state_t` without referencing it; `DownloadStateMapper.map` derives the user-visible `DownloadState`; `etaSeconds` computes the remaining-time estimate. `FileSelectionPolicy.select(files: List<TorrentFileInfo>): Selection` picks the main video file (largest video whose path doesn't look like a sample/trailer/extra) and returns per-file `FilePriority`: the main file and any subtitle track at `Normal`, everything else at `Skip`. The jlibtorrent adapter (#52) is the only caller of both.
- `com.teachermovies.torrent.api.MagnetUri`: parses `xt=urn:btih:<40 hex or 32 base32>` (plus `dn`) into a lower-case hex info-hash, shared by `FakeTorrentEngine` and the real jlibtorrent engine (#51) so both validate magnets identically.
- `com.teachermovies.torrent.fake.FakeTorrentEngine` (ADR-0003): a deterministic, in-memory `TorrentEngine` in the **main** source set, so every module above `:torrent` can drive it in tests. State lives in `MutableStateFlow`s; test-only control methods (`emitMetadata`, `advance`, `complete`, `fail`, `setEngineStatus`) and `recordedCalls` (every `setFilePriorities`/`pause`/`resume`/`remove`/`prioritizeWindow`/`prioritizeRanges`/`clearWindow` call, e.g. `remove(<id>,true)`, `prioritizeRanges(<id>,0,0+100;900+100)`) drive it deterministically -- no real time, no sleeps. `emitMetadata` applies `FileSelectionPolicy` exactly like the real engine: priorities, `TorrentSnapshot.mainFileIndex`, and `totalBytes` = the non-skipped files.
- `TorrentSnapshot.mainFileIndex: Int?`: the movie file the engine picked with `FileSelectionPolicy` when metadata arrived (null before metadata or when there is no video), so callers (Library, player) need not re-run the heuristic.
- `com.teachermovies.torrent.api.SavePathProvider`: `savePathFor(id): File`, the per-torrent payload directory; `:app-tv` wires it to `:storage`'s download layout.
- `com.teachermovies.torrent.jlib.JLibTorrentEngine(savePaths, stateDir, dispatcher)`: the real engine. The class is the only public name in `jlib`; everything else there is `internal`. `start()` opens a `SessionManager` listening on `0.0.0.0:6881,[::]:6881` with DHT on (Stopped -> Starting -> Running, or Error with `EngineError.Io`); adds need a running engine (`NotReady` otherwise). The alert listener only copies plain values into a `Channel` drained on `dispatcher.limitedParallelism(1)`, which is the one place engine state changes. Pure decisions live in `JlibMappers` (JVM-tested; no jlibtorrent types in its signatures).
- `JLibTorrentEngine` stats and control (#52): while running, a 1 s ticker on the serial dispatcher (cancelled by `stop()`) reads every handle's status into a plain `StatusSample` and republishes `torrents` via `StatusSampleMapper` (`DownloadStateMapper` + `etaSeconds`; progress x100, `totalWanted`/`totalWantedDone`, rates, `numPeers`, ratio = allTimeUpload / max(allTimeDownload, 1)). The ticker publishes the state `DownloadStateMapper` derives as-is; a move outside core-model's `canTransitionTo` table (`StatusSampleMapper.isUnexpectedTransition`, never true for an unchanged state) only logs one `Log.w` with the torrent id and both states, and `DownloadStateTransitionsTest` cross-checks every metadata-preserving pair of `RawStatus` values against that table. When metadata is known it applies `FileSelectionPolicy` with `prioritizeFiles` and sets `mainFileIndex`. `files()` is `NotReady` before metadata; `setFilePriorities` maps Skip/Normal/High to libtorrent 0/4/7 (out-of-range indices ignored); `pause`/`resume` unset auto-managed first; `remove(id, true)` uses `SessionHandle.DELETE_FILES`, and once `torrent_deleted_alert` confirms the files are gone `TorrentDirCleanup` (#229) removes the torrent's save directory (`<volume>/Movies/<id>/`, which libtorrent leaves behind) -- only if it is empty and named after the id, never recursively; a directory still holding anything (e.g. an uploaded `subs/` file) is kept, and `torrent_delete_failed_alert` or `remove(id, false)` keeps it too. Unknown ids answer `UnknownTorrent` everywhere; native failures become `EngineError.Io`.
- `JLibTorrentEngine` window API (#94) -- implemented over libtorrent piece deadlines. `prioritizeWindow` reads the handle's `TorrentInfo` (`pieceLength()`, `numPieces()`, `files().fileOffset(fileIndex)`), maps the window with `PieceWindowCalculator.piecesFor`, and applies only the delta `WindowDeadlinePlanner.plan(previous, current, deadlineStepMs)` computes against the window it last set for that torrent (remembered in engine state as its pieces in deadline order, on the serial dispatcher); `prioritizeWindow` is `prioritizeRanges` with one range, and `prioritizeRanges` builds the window with `WindowDeadlinePlanner.piecesOf` (each range's pieces ascending, ranges in the order given, shared pieces once) and plans it with the piece-list overload of `plan`: each piece that entered the window gets piece priority 7 and `set_piece_deadline`, in ascending order with deadlines `deadlineStepMs`, `2 x deadlineStepMs`, ... (the piece nearest the playback position first); each piece that left gets `reset_piece_deadline` and priority 4; pieces in both windows, or in neither, are not touched, so the same window twice applies nothing and a moving window slides. `clearWindow` calls `clear_piece_deadlines`, returns the remembered window's pieces to priority 4 and forgets it (`Ok` with no window). `rangeReadiness` answers from `readinessFor(range, pieceLengthBytes, fileOffsetInTorrent, byteOffset, lengthBytes, have)` with `have = havePiece`, the length capped at the end of the file. All three answer `UnknownTorrent` for an unknown id and `NotReady` before metadata (or for a file index the torrent lacks). `deadlineStepMs` (constructor parameter, default 100) tunes the read-ahead aggressiveness: a smaller step asks for the window's pieces sooner. The remembered windows are dropped by `remove` and `stop` (a new session has no deadlines). `WindowDeadlinePlanner`/`readinessFor` take plain values only and are JVM-tested (`WindowDeadlinePlannerTest`).
- `com.teachermovies.torrent.service` (#54): `TorrentEngineHolder` is the process's single owner of the `TorrentEngine` (`init(engine)` once, before starting the service -- a second `init` with a different instance throws; `engine` throws before `init`). `TorrentService : LifecycleService` is a typed foreground service whose type comes from the pure `ForegroundServiceTypes.forSdk(sdkInt)` (#129) -- `specialUse` on API 34+, `dataSync` on API 29..33, `0` below 29 -- passed to `ServiceCompat.startForeground` first thing in `onCreate`; it calls `engine.start()` in `onCreate` and `saveResumeData()` + `stop()` in `onDestroy`, both on the holder's serial scope so a quick restart queues behind the stop. `specialUse` is what lets downloads outlive Android 15, which caps `dataSync` at 6 h per 24 h and refuses to start a `dataSync` service from `BOOT_COMPLETED`: on API 34+ the boot autostart of #126 succeeds instead of being refused, and no time limit applies. On API 29..33, where the service still runs as `dataSync`, Android 15's `dataSync` time limit (`onTimeout`) stays as the clean-stop safety net -- for that cap and for any future one. `TorrentService.start(context)` (`ContextCompat.startForegroundService`) must be called while the app is visible or from `BOOT_COMPLETED`, which Android 15 only permits for `specialUse`; `TorrentService.stop(context)` stops it. The notification (channel `downloads`, low importance, created idempotently) shows the pure `NotificationText.format(snapshots)` (`2 descargas · 45 % · 8,3 MB/s`, `Sin descargas activas`; Completed/Error torrents are not active), re-posted at most once per 2 s (`throttleLatest`). The `:torrent` manifest declares the service with `android:foregroundServiceType="dataSync|specialUse"`, the `android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE` property inside `<service>` (the `specialUse` justification the system and Play read; see below), and `INTERNET`, `ACCESS_NETWORK_STATE`, `WAKE_LOCK`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_DATA_SYNC`, `FOREGROUND_SERVICE_SPECIAL_USE`, `POST_NOTIFICATIONS` (requesting the runtime permission is the app's job, #55). `ForegroundServiceTypesTest` pins the selector for 26, 28, 29, 33, 34 and 35 against the literal `ServiceInfo` values, so it needs no Android runtime.
- `com.teachermovies.torrent.resume` (#53): `ResumeDataStore` (`save(id, bytes)`, `loadAll(): Map<TorrentId, ByteArray>`, `load(): ResumeDataLoad` = entries + `skipped` list, `delete(id)`) and `FileResumeDataStore(dir)`, one `<dir>/<infohash>.fastresume` per torrent written atomically (`.tmp` then rename). `load` reads only `<40|64 hex>.fastresume` names; unreadable files or ones that are not a single well-formed bencoded dictionary are skipped and reported, never thrown. `JLibTorrentEngine` takes an optional `resumeData` store (default `FileResumeDataStore(<stateDir>/resume)`); it requests resume data (with the info dict) every 60 s for torrents where `needSaveResumeData()`, after an add, a metadata arrival, `pause` and `resume` (#220: without it a torrent resumed less than 60 s before a power cut came back paused), as soon as a torrent finishes (`torrent_finished_alert`; #246: without it a power cut within 60 s of completing came back `downloading` and re-downloaded the tail; the pure `ResumeSaveTriggers` picks the torrent and ignores an alert for a removed one), and for every torrent in `saveResumeData()` and `stop()` (both wait up to 10 s for the answers; `saveResumeData()` answers `Io` on a write failure or timeout, `Ok` while stopped); each `save_resume_data_alert` is written through the store, and `remove` deletes the entry. `start()` re-adds every stored torrent (`read_resume_data`) before reporting Running: stored flags (paused, auto-managed) and file priorities are kept (the automatic selection only recomputes `mainFileIndex`); entries libtorrent cannot parse are skipped and left on disk.
- `com.teachermovies.torrent.sync.EngineRepositorySync(engine, repo, scope, clock)` (#68): the one
  place that keeps `core-model`'s `TorrentRepository` in sync with a `TorrentEngine`. `start()`
  collects `engine.torrents` on `scope` and, per torrent, `upsert`s whenever a persisted field
  changed (`state`, progress rounded to one decimal, downloaded/total bytes, name, `savePath`,
  `mainFileIndex`) -- a state change writes immediately, anything else is throttled to at most once
  every 5 s (`clock`, injectable for virtual time in tests), coalescing skipped updates into the next
  one. `mainFilePath` is `savePath/<files[mainFileIndex].path>`, resolved via `engine.files(id)` the
  first time a torrent's `mainFileIndex` is seen and cached after that. `stop()` cancels the
  collection without touching `repo`. `remove(id, deleteFiles)` wraps `engine.remove` and deletes the
  row only once the engine confirms it -- the one path that deletes a row; a torrent merely missing
  from `engine.torrents` (e.g. still loading resume data right after a restart) is left alone.
  Starting this from the app is #69, out of scope here.

## Google Play `specialUse` declaration (#129)
Play Console asks for a justification for every `specialUse` foreground service. The text to paste
is the same wording as the manifest's `android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE` property:

> User-initiated peer-to-peer downloads of media the user is authorised to download, which must
> continue while the TV plays other content.

Why no other foreground-service type fits: the work is user-initiated network transfer, so `dataSync`
is the only declared type that describes it, and Android 15 caps `dataSync` at 6 h per 24 h and does
not allow starting a `dataSync` service from `BOOT_COMPLETED`. Downloading a movie over a slow link
takes longer than 6 h, and the TV must resume downloads after a reboot without the user opening the
app first (#126). `mediaPlayback` does not apply -- the service runs while nothing is playing -- and
the remaining types (location, camera, microphone, phone call, screen capture, connected device,
health, remote messaging) describe work this service does not do. Submitting the declaration is the
human's job if the app is ever published on Play; nothing in this repository does it.

## Boundaries
- No jlibtorrent type escapes this module. Other modules use `FakeTorrentEngine` in tests.

## Tests
JVM tests against the interface contract with `FakeTorrentEngine`; file-selection heuristics unit-tested; jlibtorrent integration tests optional/instrumented. `com.teachermovies.torrent.api.TorrentEngineContractTest` (in `src/test`) is the reusable, implementation-agnostic contract (`abstract fun createEngine(): TorrentEngine`); `FakeTorrentEngineTest` extends it for the fake. JVM tests never load jlibtorrent classes (the native library is Android-only), so `JLibTorrentEngine` does not extend it on the JVM; running it against the contract belongs to an instrumented test.
