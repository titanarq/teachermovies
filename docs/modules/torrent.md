# Module: torrent

**Gradle path:** `:torrent`.

## Responsibility
- `TorrentEngine` interface (see ADR-0001): add magnet / .torrent, metadata, file list, per-file priorities, pause/resume/remove, stats `Flow` (progress, speed, peers, ETA, ratio), resume data.
- jlibtorrent 2.x implementation (`JLibTorrentEngine`), running in a foreground service independent from the player.
- Automatic priority 0 for samples/images/extras; download only the movie file and `.srt`/`.ass`.
- Persisted resume data so downloads continue after reboot.
- Designed from day 1 for stream-while-downloading: piece-deadline / sequential window API around a playback position (`prioritizeWindow(fileIndex, byteOffset, windowBytes)`), even if phase 8 implements it later.
- `com.teachermovies.torrent.policy`: pure Kotlin status-mapping policy, kept separate from any adapter so it stays engine-agnostic. `RawStatus`/`RawPhase` mirror libtorrent's `torrent_status::state_t` without referencing it; `DownloadStateMapper.map` derives the user-visible `DownloadState`; `etaSeconds` computes the remaining-time estimate. `FileSelectionPolicy.select(files: List<TorrentFileInfo>): Selection` picks the main video file (largest video whose path doesn't look like a sample/trailer/extra) and returns per-file `FilePriority`: the main file and any subtitle track at `Normal`, everything else at `Skip`. The jlibtorrent adapter (#52) is the only caller of both.
- `com.teachermovies.torrent.api.MagnetUri`: parses `xt=urn:btih:<40 hex or 32 base32>` (plus `dn`) into a lower-case hex info-hash, shared by `FakeTorrentEngine` and the real jlibtorrent engine (#51) so both validate magnets identically.
- `com.teachermovies.torrent.fake.FakeTorrentEngine` (ADR-0003): a deterministic, in-memory `TorrentEngine` in the **main** source set, so every module above `:torrent` can drive it in tests. State lives in `MutableStateFlow`s; test-only control methods (`emitMetadata`, `advance`, `complete`, `fail`, `setEngineStatus`) and `recordedCalls` (for `prioritizeWindow`/`clearWindow` assertions) drive it deterministically -- no real time, no sleeps. `emitMetadata` applies `FileSelectionPolicy` exactly like the real engine: priorities, `TorrentSnapshot.mainFileIndex`, and `totalBytes` = the non-skipped files.
- `TorrentSnapshot.mainFileIndex: Int?`: the movie file the engine picked with `FileSelectionPolicy` when metadata arrived (null before metadata or when there is no video), so callers (Library, player) need not re-run the heuristic.
- `com.teachermovies.torrent.api.SavePathProvider`: `savePathFor(id): File`, the per-torrent payload directory; `:app-tv` wires it to `:storage`'s download layout.
- `com.teachermovies.torrent.jlib.JLibTorrentEngine(savePaths, stateDir, dispatcher)`: the real engine. The class is the only public name in `jlib`; everything else there is `internal`. `start()` opens a `SessionManager` listening on `0.0.0.0:6881,[::]:6881` with DHT on (Stopped -> Starting -> Running, or Error with `EngineError.Io`); adds need a running engine (`NotReady` otherwise). The alert listener only copies plain values into a `Channel` drained on `dispatcher.limitedParallelism(1)`, which is the one place engine state changes. Pure decisions live in `JlibMappers` (JVM-tested; no jlibtorrent types in its signatures).
- `JLibTorrentEngine` stats and control (#52): while running, a 1 s ticker on the serial dispatcher (cancelled by `stop()`) reads every handle's status into a plain `StatusSample` and republishes `torrents` via `StatusSampleMapper` (`DownloadStateMapper` + `etaSeconds`; progress x100, `totalWanted`/`totalWantedDone`, rates, `numPeers`, ratio = allTimeUpload / max(allTimeDownload, 1)). When metadata is known it applies `FileSelectionPolicy` with `prioritizeFiles` and sets `mainFileIndex`. `files()` is `NotReady` before metadata; `setFilePriorities` maps Skip/Normal/High to libtorrent 0/4/7 (out-of-range indices ignored); `pause`/`resume` unset auto-managed first; `remove(id, true)` uses `SessionHandle.DELETE_FILES`. `prioritizeWindow`/`clearWindow` answer `Unsupported` until E7; unknown ids answer `UnknownTorrent` everywhere; native failures become `EngineError.Io`.
- `com.teachermovies.torrent.service` (#54): `TorrentEngineHolder` is the process's single owner of the `TorrentEngine` (`init(engine)` once, before starting the service -- a second `init` with a different instance throws; `engine` throws before `init`). `TorrentService : LifecycleService` is a `dataSync` foreground service (manifest type + `FOREGROUND_SERVICE_DATA_SYNC`, typed `ServiceCompat.startForeground` first thing in `onCreate`); it calls `engine.start()` in `onCreate` and `saveResumeData()` + `stop()` in `onDestroy`, both on the holder's serial scope so a quick restart queues behind the stop. Android 15's `dataSync` time limit (`onTimeout`) stops the service cleanly. `TorrentService.start(context)` (`ContextCompat.startForegroundService`) must be called while the app is visible; `TorrentService.stop(context)` stops it. The notification (channel `downloads`, low importance, created idempotently) shows the pure `NotificationText.format(snapshots)` (`2 descargas · 45 % · 8,3 MB/s`, `Sin descargas activas`; Completed/Error torrents are not active), re-posted at most once per 2 s (`throttleLatest`). The `:torrent` manifest declares the service and `INTERNET`, `ACCESS_NETWORK_STATE`, `WAKE_LOCK`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_DATA_SYNC`, `POST_NOTIFICATIONS` (requesting the runtime permission is the app's job, #55).
- `com.teachermovies.torrent.resume` (#53): `ResumeDataStore` (`save(id, bytes)`, `loadAll(): Map<TorrentId, ByteArray>`, `load(): ResumeDataLoad` = entries + `skipped` list, `delete(id)`) and `FileResumeDataStore(dir)`, one `<dir>/<infohash>.fastresume` per torrent written atomically (`.tmp` then rename). `load` reads only `<40|64 hex>.fastresume` names; unreadable files or ones that are not a single well-formed bencoded dictionary are skipped and reported, never thrown. `JLibTorrentEngine` takes an optional `resumeData` store (default `FileResumeDataStore(<stateDir>/resume)`); it requests resume data (with the info dict) every 60 s for torrents where `needSaveResumeData()`, after an add, a metadata arrival and `pause`, and for every torrent in `saveResumeData()` and `stop()` (both wait up to 10 s for the answers; `saveResumeData()` answers `Io` on a write failure or timeout, `Ok` while stopped); each `save_resume_data_alert` is written through the store, and `remove` deletes the entry. `start()` re-adds every stored torrent (`read_resume_data`) before reporting Running: stored flags (paused, auto-managed) and file priorities are kept (the automatic selection only recomputes `mainFileIndex`); entries libtorrent cannot parse are skipped and left on disk.
- `com.teachermovies.torrent.sync.EngineRepositorySync(engine, repo, scope, clock)` (#68): the one
  place that keeps `core-model`'s `TorrentRepository` in sync with a `TorrentEngine`. `start()`
  collects `engine.torrents` on `scope` and, per torrent, `upsert`s whenever a persisted field
  changed (`state`, progress rounded to one decimal, downloaded/total bytes, name, `savePath`,
  `mainFileIndex`) -- a state change writes immediately, anything else is throttled to at most once
  every 5 s (`clock`, injectable for virtual time in tests), coalescing skipped updates into the next
  one. `mainFilePath` is `savePath/<files[mainFileIndex].path>`, resolved via `engine.files(id)` the
  first time a torrent's `mainFileIndex` is seen and cached after that. `stop()` cancels the
  collection without touching `repo`. `remove(id, deleteFiles)` wraps `engine.remove` and deletes the
  row only once the engine confirms it -- the one path that deletes a row; a torrent merely missing
  from `engine.torrents` (e.g. still loading resume data right after a restart) is left alone.
  Starting this from the app is #69, out of scope here.

## Boundaries
- No jlibtorrent type escapes this module. Other modules use `FakeTorrentEngine` in tests.

## Tests
JVM tests against the interface contract with `FakeTorrentEngine`; file-selection heuristics unit-tested; jlibtorrent integration tests optional/instrumented. `com.teachermovies.torrent.api.TorrentEngineContractTest` (in `src/test`) is the reusable, implementation-agnostic contract (`abstract fun createEngine(): TorrentEngine`); `FakeTorrentEngineTest` extends it for the fake. JVM tests never load jlibtorrent classes (the native library is Android-only), so `JLibTorrentEngine` does not extend it on the JVM; running it against the contract belongs to an instrumented test.
