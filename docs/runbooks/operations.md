# Operations runbook -- teachermovies agent OS

How to watch, pause and patch the agent mechanism (`agent_os/`, never edited here) on this host.
Background: `agent_os/docs/AGENT_OS.md` §2.4, §6, §8 and `.claude/agents/control-plane.md` Duty 5.

## Units (systemd --user)

| unit | what | every |
|---|---|---|
| `teachermovies-guard.timer` | `scripts/agent_guard.py tick`: budget/liveness/quota check, writes planner events, wakes the planner | 5 min |
| `teachermovies-board-sync.timer` | `scripts/board_sync.py`: mirrors `status:*` labels to the Project 2 Status column (below) | 5 min |
| `teachermovies-gradle-cleanup.timer` | `scripts/stop_idle_gradle_daemon.sh`: stops the shared idle Gradle daemon before it settles in the guard's cgroup (#305, below) | 30 min |

Unit files for the board sync and for the Gradle daemon cleanup are versioned in `scripts/systemd/`;
the guard's are generated by `agent-os-install`. After editing any of them:
`systemctl --user daemon-reload`. The Gradle cleanup timer is versioned but **not installed yet**:
install it once `scripts/stop_idle_gradle_daemon.sh` is on `main` (command below, under
"Left-over processes in the guard's cgroup").

## Monitor

```sh
systemctl --user list-timers --no-pager | grep teachermovies        # both timers armed?
journalctl --user -u teachermovies-guard.service --since "1 hour ago" -o cat \
  | grep -vE "never started|^0 event|nothing to wake" | tail -40      # tick output
scripts/worker_progress.sh                                           # every backend, last hour
scripts/worker_progress.sh --hours 6 37 qwen                         # one issue / backend
cat .cache/worker_qwen.issue .cache/worker_qwen.state                # what the qwen worker holds
tail -5 .cache/planner/runs.tsv .cache/refiner/runs.tsv              # role runs + cost (USD)
scripts/issues.py list --label status:doing                          # likewise ready/review/blocked-on-human
gh pr list --state open
git -C ../teachermovies-qwen log --oneline -5                        # worker branch commits
```

Qwen reports no cost: report its spend in tokens (`worker_progress.sh`), never as 0 USD.
Alarms: an `EXPECT` past its `cutoff` with no later line; a Qwen issue past ~60 M tokens; a
`blocked-on-human` older than an hour; a timer inactive. Never `cat` a `.jsonl` stage log.

## Pause / resume

- Full stop (the tick returns before doing anything): put `status:agents-paused` on the tracking
  epic #1 -- `scripts/issues.py update 1 --add-label status:agents-paused`; remove it to resume.
  This is the human's lever. A running worker is not killed by it; it is cut at its next check.
- Stop ticking altogether: `systemctl --user disable --now teachermovies-guard.timer`
  (re-arm: `systemctl --user daemon-reload && systemctl --user enable --now teachermovies-guard.timer`).
- Wake the planner early: comment the reason, then `scripts/issues.py update N --add-label wake:planner`.

## Board sync (titanarq/agent-os#14, fixed upstream)

`scripts/board_sync.py` was written because `issues.py move` could not find org project 2's items
(agent-os#14). That is fixed upstream (agent-os PR #26: `move` resolves the item through
`issue.projectItems`; agent-os#23, PR #47: `issues.py create` adds the issue to the board), and
the subtree carries it since the 36985fc pull. The sync is kept for now because it also does what
the mechanism does not: it adds issues created outside `issues.py create` to the board and moves
closed issues to Done. It resolves items through GraphQL `issue.projectItems`, sets Status per
`project.board_columns` (no status label -> Backlog, closed -> Done, `blocked-on-human` -> left as
is), is idempotent and quiet; preview with `scripts/board_sync.py --dry-run`. Retire it (script,
`scripts/systemd/teachermovies-board-sync.*`, the installed unit) once the board is confirmed to
stay in step without it.

The installed unit is a copy: after changing `scripts/systemd/teachermovies-board-sync.*`, copy it
to `~/.config/systemd/user/` and `systemctl --user daemon-reload`.

## CI runners

CI runs on **GitHub-hosted runners** (`runs-on: ubuntu-latest`) since the repo went public
(2026-09-24). The self-hosted runners that used to run it on this machine (`Titan-tm-1..4`) were
deregistered and deleted the same day.

**Rule: self-hosted runners must never be registered for this public repo** -- any fork PR could
run arbitrary code on the machine. The org's Default runner group keeps "Allow public
repositories" **OFF**:

```sh
gh api orgs/titanarq/actions/runner-groups -q '.runner_groups[] | "\(.name) public=\(.allows_public_repositories)"'
```

## Interaction limit

Since going public, the repo has an interaction limit of `collaborators_only` (only collaborators
can open issues/PRs or comment), so outsiders cannot feed text to the agents. It expires after
six months; check and renew it:

```sh
gh api repos/titanarq/teachermovies/interaction-limits
gh api -X PUT repos/titanarq/teachermovies/interaction-limits -f limit=collaborators_only -f expiry=six_months
```

## Left-over processes in the guard's cgroup (#305)

`journalctl --user -u teachermovies-guard.service` logs two families of lines about processes still
in the unit's cgroup: `Found left-over process <pid> (<name>) in control group while starting unit.
Ignoring.` (1751 lines over the 2 days to 2026-09-28 08:09, 927 distinct PIDs) and `Unit process
<pid> (<name>) remains running after unit stopped.` (2123 over the same window). For a dispatched
run and its build both are **expected**: the tick is `Type=oneshot`, so `ExecStart` returns while the
worker it launched keeps running inside the same cgroup, and `KillMode=process` -- rendered by
`agent-os-install` from `agent_os/templates/systemd/override.conf.tmpl`, deliberately -- tells
systemd not to kill it. `KillMode=control-group` on that unit is not the fix: it would SIGKILL the
run about 90 s into it, at the end of the tick that launched it.

**Discriminator when reading those lines: a PID that changes every few minutes is the live run; the
same PID across many consecutive ticks is a leak.** (Diagnosis stage of #305, 07:23: of the PIDs
logged over 2 days, 7 were still alive, and 5 of those were the run in flight.) The one genuine leak
class measured was a shared persistent Gradle daemon -- PID 3356603, RSS 2.30 GB, 11.7 h old,
`PGID = SID = its own PID`, sitting in `.../app.slice/teachermovies-guard.service` while that unit
had been `inactive (dead)` since 07:14 -- plus the Kotlin compile daemon it had started (PID
3365668, RSS 4.16 GB, same session). 266 journal lines named those two over the 2 days, and they
also polluted the dead unit's accounting (`Tasks: 143`, `Memory: 10.3G (peak: 16.3G)` at 07:16).
Both escape the run's `kill -TERM -<pgid>` cut *and* `KillMode=process`, because the daemon starts
its own session. `scripts/test.sh` is not the source: it passes `--no-daemon` (line 94), whose
single-use daemon exits with the build; this one came from a direct `./gradlew` call, which the
worker rules forbid for exactly this reason.

Fix applied on the host side (nothing under `agent_os/`):

- `gradle.properties` sets `org.gradle.daemon.idletimeout=1800000`: a daemon no build has used for
  30 min expires instead of lasting Gradle's 3 h default.
- `scripts/stop_idle_gradle_daemon.sh` stops the daemon when `./gradlew --status` reports it IDLE and
  no Gradle client JVM is alive anywhere on the host, and refuses (saying why) otherwise --
  `~/.gradle` is a symlink to `/mnt/data/titan-cache/gradle`, so every worktree shares one daemon
  registry and `--stop` would kill a build another agent has in flight. Preview with `--dry-run`.
  The Kotlin compile daemon needs no branch of its own: measured 2026-09-28, both were gone 12 s
  after a `--stop` that itself took ~2 s and needed no `ANDROID_HOME`.
- `scripts/systemd/teachermovies-gradle-cleanup.{service,timer}` run that script every 30 min as a
  backstop for a daemon the idle timeout does not retire (one started before the property landed, or
  kept warm by a build every few minutes). Not installed yet: the script reaches the main checkout
  only when this merges. Then install it the way the board sync is installed --

  ```sh
  cp scripts/systemd/teachermovies-gradle-cleanup.* ~/.config/systemd/user/
  systemctl --user daemon-reload && systemctl --user enable --now teachermovies-gradle-cleanup.timer
  ```

Effect of one cleanup run, measured: the tick at 08:05:33 -- the first after the 08:02:37 stop --
logged 3 left-over lines, all of them this run's own tree (`bash` + `node` + `node`), and none naming
either daemon PID.

**What remains open:** the two message families themselves. While a run is in flight, its own
processes (and, during a build, its JVMs and `aapt2`) stay in the guard's cgroup and are logged once
per tick, and the dead unit's accounting carries them. Silencing that needs the launcher to give each
run its own scope or slice with `KillMode=control-group`, which is upstream -- see the bullet in "To
report upstream" below.

## To report upstream (titanarq/agent-os)

- **Worker-class fallback Qwen -> Claude on Qwen quota exhaustion.** The human's rule
  (2026-09-26): a task on a Qwen worker class (`mechanical-qwen`, `complex-qwen`) may move to
  Opus (`claude` / `claude-opus-5-5`) when Qwen's quota is exhausted; an Opus task
  (`complex-claude`) must never fall back to Qwen. agent_os cannot express the first half today:
  `TaskClass.fallback:` parses on any class, but only the one-shot role drivers
  (`agent_os/bin/agent_task.sh`, `planner_task.sh`, through `agent_os.lib role-backend`) read it
  at launch; `worker_task.sh` never does, and `qwen_fallback_eligible` only authorises the
  planner's Claude -> Qwen redispatch. Declaring `fallback:` on a Qwen worker class would be
  inert for the launch and would also make `allows_backend_fallback` true, silencing the guard's
  `quota_exhausted_no_fallback` page for a run nothing can reroute. So the Qwen classes stay
  without a fallback until agent_os supports a worker launch gate (or a planner redispatch in the
  Qwen -> Claude direction).
- **The control plane's prompt forbids Claude worker classes.** `agent_os/agents/control-plane.md`
  (rendered to `.claude/agents/control-plane.md`) says never to assign a worker task to a Claude
  backend, although this project now defines a Claude worker class (`complex-claude`), so every
  issue the control plane writes gets a Qwen class. Neither file is edited here. Workaround until
  upstream fixes it: the control plane keeps writing Qwen classes; the refiner (whose class rule
  in `config/agent_prompts/refiner.md` lists `complex-claude`) or an explicit human decision may
  assign `complex-claude`.

- **A `CHANGES_REQUESTED` review cannot be handed back to a worker once every stage of
  its task is already committed.** Found on #267 / PR #298 (2026-09-27): the validator
  requested changes on a one-stage task whose single stage was already committed and
  clean. The planner tried to resume qwen on it, but `agent_os/bin/worker_task.sh`'s
  `launch_stage` always starts from the first pending stage; with none pending it stops
  ("all N stage(s) ... already committed") instead of launching a fix pass with the
  review as context. Worse, qwen had since started a different issue (#279), so
  `.cache/worker_qwen.issue` no longer even pointed at #267 -- a plain `resume` would
  have picked up the wrong task. The planner could not route around this itself and
  posted the question to the human instead. Workaround until agent_os supports
  relaunching a completed-stage task on review feedback: the human (or the control
  plane, once the human decides) adds a second stage to the task body naming the fix, so
  the next planner pass launches it as ordinary pending work with the review as context;
  or, files a follow-up task on the PR's branch; or fixes it directly on the PR.

- **A stage whose deliverable is a merge commit can never be closed.** Found on #267 / PR #298
  (2026-09-27, 18:31 UTC): stage 3/3 asked the worker to merge `origin/main` into the PR branch
  and resolve a conflict, "one commit (the merge commit)". The worker did exactly that (merge
  commit `stage 3/3: ...`, tests green), but `agent_os/bin/worker_task.sh`
  (`resolve_stage_context`) counts stages with `git log --first-parent --no-merges`, so the merge
  commit is invisible to the counter; `stage-exit` saw 2/3, wrote
  `CUT_BY_GUARD reason=no_stage_commit` and nothing was pushed. A regular commit carrying the
  resolved text instead of the merge does not help either: `open-pr` merges the base before
  pushing and conflicts again on the same hunk. Workaround until agent_os counts a merge commit
  whose subject is `stage N/M: ...` (or offers a "merge the base" stage kind): word such a stage as
  "merge the base if `git merge-base --is-ancestor origin/<base> HEAD` fails, resolving as
  quoted; then close the stage with `git commit --allow-empty` and the `stage N/M:` subject; no
  rebase, reset or force push" (as #267's stage 3/3 now reads).

- **The validator can approve a PR having run only the module test named in the Definition
  of done, not the full `scripts/test.sh`.** Found on #294 / PR #307 (2026-09-27): the
  validator approved with only `:assistant:test` green; the new `spokenOutput` setting
  defaults all-off, and three `:app-tv` `PlayerViewModelTest` cases that never pass
  `SpokenOutputSettings` expect speech, so CI on the head SHA came back red (AGENTS.md:
  every PR must leave `scripts/test.sh` green). The control plane caught it at merge time
  (Duty 4, condition 1) before merging, and added a second stage to #294's body instead.
  Workaround until the validator itself runs the full `scripts/test.sh` rather than only the
  module target named in the Definition of done: the control plane keeps reading CI on the
  head SHA as the authority, never the validator's own narrower run, before merging.

- **The validator's own worktree has no Android SDK, so it cannot run `scripts/test.sh` at
  all and escalates a question CI has already answered.** Found on #273 / PR #327
  (2026-09-28): the validator requested changes with its test line "NOT SETTLED ... No test
  ran" -- Gradle stopped at `SDK location not found. Define a valid SDK location with an
  ANDROID_HOME environment variable or by setting the sdk.dir path in your project's local
  properties file`, because the review worktree has neither `local.properties` nor those
  variables. `config/agents.yaml`'s `project.worker_environment` does carry
  `ANDROID_HOME`/`ANDROID_SDK_ROOT`, but only `agent_os/bin/worker_task.sh` reads it (its
  `worker-environment` export loop); the validator is a one-shot role launched by
  `agent_os/bin/agent_task.sh`, which prepares a throwaway worktree under `.cache/` and never
  exports it, so the review environment is SDK-less by construction. The validator then raised
  a `status:blocked-on-human` doubt asking the human to choose between fixing that environment
  and running the tests by hand, when the answer was already on the record: CI on head
  `1887a7b` was red for exactly one reason, ktlint's max line length at
  `http-server/src/test/kotlin/com/teachermovies/http/WebUiRouteTest.kt:154` (122 characters,
  limit 120). The human ruled it settled that way on #273 (02:00 UTC). Workaround already in
  effect, the same one as the #294 / PR #307 bullet above -- no code change here: the control
  plane reads CI on the PR's head SHA as the authority on whether tests pass, never the
  validator's own (possibly SDK-less) run, before merging or before answering a
  `blocked-on-human` doubt of this shape. The fix itself is upstream: let the validator's launch
  path read `project.worker_environment` too, or give the review worktree an environment key of
  its own.

- **A dispatched run stays inside the guard unit's own cgroup, so systemd reports it as a left-over
  process at every tick and the dead unit's accounting carries its memory.** Found on #305
  (2026-09-28): the tick is `Type=oneshot` and `KillMode=process` is deliberate (`control-group`
  would SIGKILL the run the tick just launched), so the run and its Gradle build outlive `ExecStart`
  inside `teachermovies-guard.service` -- 1751 `Found left-over process ... Ignoring.` and 2123
  `Unit process ... remains running after unit stopped.` lines over 2 days, and `Tasks: 143` /
  `Memory: 10.3G (peak: 16.3G)` attributed to a unit that was `inactive (dead)`. The host side now
  mitigates the one measured leak class -- a shared persistent Gradle daemon, which escapes the run's
  `kill -TERM -<pgid>` cut as well because it starts its own session -- under "Left-over processes in
  the guard's cgroup" above. The durable fix is upstream: launch each run in its own
  `systemd-run --scope` (or a per-run slice) with `KillMode=control-group`, so the whole tree --
  including a `setsid` grandchild such as a Gradle daemon or an MCP `chrome-devtools` server -- is
  reaped when the run ends, and none of it is counted against the guard unit.
